# Full revision candidate queue

This queue searches the national residential planning table for an earlier refused application followed by a later granted application that may represent a revised version of the same physical development.

## Outputs

- `full_revision_candidate_queue.csv`: complete candidate queue. Existing manual audit decisions are carried forward where keys match.
- `full_revision_manual_review_sample.csv`: deterministic first review batch, with 100 pending candidates from each linkage-strength tier.
- `full_revision_manual_review_pilot.csv`: smaller starting batch, with 30 pending candidates from each tier. Complete this first before committing to the remaining calibration sample.
- `full_revision_linkage_diagnostics.json`: scope, blocking counts, tier counts, configuration and recall against known accepted pairs.
- `full_revision_double_review_slice.csv`: deterministic, label-masked second-review slice (8 resolved rows per tier) built from the completed pilot. Complete `double_review_status`, `double_review_notes`, `reviewer_b` and `reviewed_at_b`, then save as `full_revision_double_review_slice_fixed.csv`.
- `full_revision_double_review_diagnostics.json`: slice configuration and row counts.
- `full_revision_double_review_adjudication.csv` and `full_revision_double_review_agreement_summary.json`: generated by `adjudicate_revision_double_review.py` after the second review. Disagreements and unresolved rows are flagged `adjudication_required` with blank `adjudicated_status`; they are never auto-resolved.
- `linkage_ranking_experiment_results.json` and `linkage_ranking_labelled_frame.csv`: conservative held-out evaluation of candidate ranking using the manual labels only (see "Ranking experiment" below).

## Matching rules

Candidates must be within the same planning authority, have a refusal before a later grant, use different base application references and fall within the configured eight-year window. Candidate generation uses exact normalized address and/or coordinates within 50 metres. Very large blocks are excluded to prevent candidate explosions at generic addresses or dense coordinate cells.

`linkage_score` is a transparent heuristic strength score based on blocking method, address, coordinate distance, description similarity, applicant and postcode. It is not a probability and no tier is automatically accepted.

## Manual review

Start with `full_revision_manual_review_pilot.csv`. For each row:

1. Open both source links.
2. Decide whether the later application is genuinely a revised submission for the same physical development—not merely another application at the same address.
3. Set `manual_review_status` to `accepted`, `rejected`, or leave it `pending` if uncertain.
4. Record the reason in `manual_review_notes` and optionally add `reviewer` and `reviewed_at`.

Review the first batch before defining any automatic acceptance threshold. A second reviewer should independently check a sample from every tier and all disputed cases.

## Double review and adjudication

The double-review slice is label-masked so the second reviewer decides without seeing reviewer A's call. After completing `full_revision_double_review_slice_fixed.csv`:

```powershell
$env:PYTHONPATH = (Resolve-Path '02_development/scripts').Path
python 02_development/scripts/adjudicate_revision_double_review.py
```

The adjudication output records reviewer agreement and time per tier. Agreement is a reviewer-consistency check only; it does not validate pairs against source documents and is never used to auto-accept candidates. Any pair where the reviewers disagree, or where reviewer B left a row unresolved, must be adjudicated manually.

## Ranking experiment

`build_linkage_ranking_experiment.py` evaluates whether the current tier-then-score order prioritises candidates worth reviewing, using the manually labelled rows (pilot, audit and completed 300-row sample: 415 resolved labels, 261 accepted / 154 rejected) as ground truth.

Current results (5-fold stratified holdout over the labelled rows): mean ROC-AUC 0.932 (fold range 0.891-0.962), mean average precision 0.943, mean precision 0.873, mean recall 0.943. A trained ranker on the same features performs essentially the same as the plain heuristic (ROC-AUC 0.932 vs 0.934 without the score/tier features), so the existing linkage_score and tier order are a sound review-priority signal.

Per-tier held-out precision (mean across folds): high 0.93, medium 0.85, low 0.56. Reviewing the queue high-to-low tier in score order surfaces about 75% of accepted labels in the top 10% of the queue and 93% in the top 20%.

These numbers only describe the labelled subset. The labels are not a random sample of the queue (the pilot was tier-stratified and the audit came from the earlier narrow queue), so they are not national precision/recall estimates, and no threshold auto-accepts candidates. Practical guidance: keep auditing manually, prioritise the high tier (93% labelled precision), continue medium-tier audits, and treat low-tier bulk auditing as low-yield (about 14% acceptance in the labelled low-tier rows).
