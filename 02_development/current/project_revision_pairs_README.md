# Project revision-pair candidate queue

`project_revision_pairs.csv` is an audit queue, not a causal training set and not a submission-time model input.

Generated by:

```powershell
$env:PYTHONPATH = (Resolve-Path .vendor).Path
python 02_development/scripts/build_project_revision_pairs.py
```

## Matching policy

- A pair must be time ordered: a refused application followed by a granted application.
- `SiteId` is only used together with planning authority. It is not nationally unique.
- The fallback requires the same normalized authority/address, exactly two applications at that address, and description-token similarity of at least 0.30.
- Fallback matches are deliberately low-confidence (`<= 0.90`) and require manual audit.
- Generic multi-application addresses are excluded from the fallback to avoid combining unrelated developments.

## Review procedure

Review `project_revision_pair_audit.csv` before using any pair as evidence. Confirm the same physical project/site, verify the original/refined scheme relationship from source documents, and correct the extracted feature delta only where both values have provenance. Record false-match patterns in the audit notes.

The queue currently stores application case keys because historical scheme IDs do not yet exist. Future canonical Site/Application/Scheme migrations should map accepted pairs to durable scheme records.

## Accepted evidence export

The first manual review accepted 46 pairs, rejected 3 and left 10 pending. Regenerate the evidence-only exports after each audit update:

```powershell
python 02_development/scripts/build_accepted_revision_pair_exports.py
```

- `accepted_revision_pairs.csv` contains only manually accepted pairs and the review note.
- `accepted_revision_pair_group_map.csv` gives the two member cases a deterministic project-group ID for evaluation splitting. It is evaluation/evidence metadata, never a submission-time predictor.
